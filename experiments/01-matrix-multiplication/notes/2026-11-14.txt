** 2. Layouts (task 1 and 2)

Until the morning only row major was used: element (i, j) is at i * n + j.
Now there are three layouts (see main.cpp). The input is generated in row major, converted to the
layout before timing, and the result is converted back for the check. The conversion is O(n^2)
and not timed.
  row major     (i, j) at i * n + j
  column major  (i, j) at j * n + i
  tile wise     T x T tiles, each tile stored as one contiguous block (row major inside the tile),
                the tiles stored one after another. n must be a multiple of T.

Hypothesis (from theory) for column major, to be confirmed or rejected by the measurement of
col_wise against row_wise (it was first planned to skip it if it only mirrors row major):

Column major is the mirror image of row major: element (i, j) is at j * n + i.
In C[i][j] += A[i][k] * B[k][j], what matters is which direction the inner loop walks.
  loop order i,j,k: A along a row, B down a column
  loop order i,k,j: B along a row, C along a row   (fast in row major)
  loop order j,k,i: A down a column, C down a column (fast in column major)
So column major with a matching loop order should just rotate the result, not change it:
  row major    + i,k,j  = fast     column major + j,k,i  = fast
  row major    + i,j,k  = slow     column major + i,j,k  = slow (one strided stream, same as before)
  column major + i,k,j  = slowest (B and C both strided)
Expectation: col_wise (j,k,i on column major) about as fast as row_wise (i,k,j on row major).
Not measured yet. If it is confirmed, the thesis can say that column major mirrors row major.

Tile wise layout (each T x T tile stored contiguous) is NOT only a mirror. Possible differences:
  - the tile is one block, so no cache line is half used
  - no conflict misses from the row distance (at n=1024 rows are exactly 8 KiB apart)
  - fewer TLB misses (a 32x32 tile in row major touches 32 pages, contiguous 2 pages)
So this one may change the numbers. tiled (row major) against tiled_tile_wise (same loops, same
tile size, only the layout differs) isolates exactly this effect.


** 3. Theory: tile size (cache aware)

The tiled version splits C = A * B into T x T tiles. For one (ii, jj, kk) step it uses a tile of A,
a tile of B and a tile of C and computes all of C-tile += A-tile * B-tile before moving on.
In the code (main.cpp) the loops are i, k, j inside the tile, so B-tile is read T times
(once per row i) and a row of the C-tile is reused T times (over k).

Size of a tile = T * T * 8 bytes (double).
  B-tile alone (the part reused most):  8 * T^2
  A, B and C tile together:            24 * T^2

This machine (AMD Ryzen 5 5500U): L1d 32 KiB per core, L2 512 KiB per core, L3 4 MiB shared.

  T      B-tile      3 tiles      fits (3 tiles)
  4      128 B       384 B        L1 (but tiny)
  8      512 B       1.5 KiB      L1
  16     2 KiB       6 KiB        L1
  32     8 KiB       24 KiB       L1  (the size used so far)
  64     32 KiB      96 KiB       L2  (B-tile alone = whole L1)
  128    128 KiB     384 KiB      L2
  256    512 KiB     1.5 MiB      L3  (B-tile alone = whole L2)
  512    2 MiB       6 MiB        no (more than L3)

Memory traffic (why tiling helps): row_wise reads all of B again for every row i, that is about
n^3 numbers from the level where B lives. With tiles, each tile is loaded once per step and reused
T times, so the traffic is about 2 * n^3 / T numbers. Bigger T = less traffic, but only while the
tiles stay in the cache level. This is the trade-off the sweep measures.

What if the tile does not fit in cache?
  The tile is then reused from the next, slower level (L1 -> L2 -> L3 -> RAM). There is no sudden
  break, the speed drops in steps, one step per cache level. When T >= n the whole matrix is one tile
  and tiled is the same as row_wise (the edge tiles are cut with std::min).

Cases from the professor, for this machine (one matrix = 8 * n^2 bytes, one row = 8 * n bytes):

  n      one row    one matrix    case
  64     0.5 KiB    32 KiB        matrix about the size of L1, everything fits
  256    2 KiB      512 KiB       matrix = L2 size
  512    4 KiB      2 MiB         matrix fits in L3 only
  1024   8 KiB      8 MiB         whole matrix > cache > single row  (matrix larger than L3, row fits L1)
  2048   16 KiB     32 MiB        same case, two rows (B and C) = 32 KiB = whole L1, so L1 starts to be tight
  4096   32 KiB     128 MiB       single row = L1 size
  8192   64 KiB     512 MiB       single row > L1 (L2 would need n > 65536, not reachable)

  Whole matrix > cache > single row: row_wise streams B again for every row i, memory bandwidth
    limits it (2.9 GFLOPS at n=1024 against 7.9 at n=512). Tiling should help.
  Single row > cache: even the C row can no longer stay in L1 while k runs, so row_wise also loses
    that reuse and gets slower again. Tiling should matter even more. Needs n >= 4096.

Prediction (hypothesis, to be compared with the measurement, not a result):
  - T = 4, 8: slower than T = 16..64 (loop overhead and little reuse)
  - T = 16..64: best, tiles fit L1/L2
  - T = 128, 256: slower than the best, tiles only fit L2/L3
  - T = 512 (and T >= n): close to row_wise
  - so a U shaped curve with the minimum time around T = 16..64
  - at n <= 512 little or no gain over row_wise (as seen with T = 32 in October)
  - T = 64 may be worse than expected because of conflict misses when n is a power of two


** 4. Theory: cache oblivious, and the nine versions

Cache aware = the algorithm is tuned to the cache: the tile size T is chosen to fit a cache level.
It needs a new T for every machine, and one T fits one level (L1 or L2), not all.

Cache oblivious = the algorithm never uses the cache size. C += A * B is split recursively: the
largest of the three dimensions (rows of C, columns of C, shared dimension k) is cut in half, the
two halves are done one after the other, and so on until the block is small. Whatever the cache
size is, at some depth of the recursion the blocks (side about sqrt(cache size / 3 / 8) doubles)
fit into it, and all the work below that depth runs inside the cache. This works for L1, L2 and
L3 at the same time, because every level of the recursion is a "tile" of a different size.
Known result: this does as few cache misses (order n^3 / (line size * sqrt(cache size))) as the best
tiling, without knowing the cache.

Costs and limits:
  - recursion has call overhead, so the recursion stops at a small block ("base"), where plain
    loops run. The base only controls the overhead, it is not tuned to a cache. Parameter list in
    the experiment shows if the result depends on it.
  - on row major (and column major) a block is not contiguous: its rows are n * 8 bytes apart. At
    n = power of 2 this can cause conflict misses (see section 3), also for the recursion.
  - oblivious_tile_wise recurses over whole tiles, so the tile size T is in the layout. The
    recursion is oblivious, the layout is not: it is a hybrid. A fully oblivious layout is Z order
    (Morton), which is not implemented.
  - the k halves are done in order, so each element of C is summed in the same order as in all other
    versions and all checksums stay identical.

The nine versions (main.cpp), parameter = last number on the command line:

                    row major             column major          tile wise
  plain loops       row_wise              col_wise              -
  cache aware       tiled                 tiled_col_major       tiled_tile_wise
  cache oblivious   oblivious_row_major   oblivious_col_major   oblivious_tile_wise
  (naive = textbook i,j,k on row major, kept as the reference)

  parameter of tiled, tiled_col_major, tiled_tile_wise, oblivious_tile_wise = tile size T
  parameter of oblivious_row_major, oblivious_col_major = smallest block of the recursion

Predictions (hypotheses, to be compared with the measurement, not results):
  1. oblivious is close to the best cache aware version without any tuning, maybe 10% to 30%
     slower because of the recursion overhead.
  2. At n >= 1024 (matrix larger than L3) oblivious is clearly faster than the plain loops.
  3. Column major versions mirror the row major versions.
  4. Tile wise layout is at least as fast as row major, most visible when n is a power of 2 and
     large (no conflict misses, fewer TLB misses).
  5. The oblivious versions hardly depend on the base parameter, as long as it is not tiny.
     (Tile size of the cache aware versions does matter, see section 3.)


** 5. What was implemented today

  - main.cpp: optional 5th argument "reference" (naive or row_wise). The result is checked against
    this version before timing. Default is naive, as before, so old commands and old results are
    unchanged. For n > 1024 the naive check takes minutes, so row_wise is used there.
  - main.cpp: the six new versions of the table in section 4 (col_wise, tiled_col_major,
    tiled_tile_wise, oblivious_row_major, oblivious_col_major, oblivious_tile_wise) and the layout
    conversions. Tested for correctness: every run is checked against the reference before
    timing. All nine versions give the same checksum at n=96. The row major and column major
    versions also at n=100 and n=131 (not multiples of the tile or the base); the tile wise
    versions need n to be a multiple of the tile and refuse other sizes.
  - scripts/checks/tile_sweep.sh: new check "tile_sweep". For each matrix size: one row_wise run as
    the baseline, then every version in TILE_SWEEP_VERSIONS for every tile size. Writes
    tile-sweep.csv. All rows for the same n must have the identical checksum, otherwise the script
    stops with an error. The professor asked specifically for the tile wise layout with different
    tile sizes, so the default versions are tiled (row major) and tiled_tile_wise (tile wise, each
    tile contiguous), with the same tile sizes, so the layout is the only difference. The tile wise
    version cannot run when the tile does not divide n (for example T=512 at n=256: the tile
    would be larger than the matrix); those combinations are skipped with a message and are
    missing from the CSV. T = n (one tile) is allowed.
  - scripts/checks/oblivious.sh: new check "oblivious". For each matrix size: row_wise and col_wise,
    then the six parameter versions once per value of OBLIVIOUS_PARAMS. Writes oblivious.csv.
    Same checksum check as tile_sweep. Tile wise versions need n to be a multiple of the tile size.
  - benchmark.conf: TILE_SIZES, TILE_SWEEP_VERSIONS, TILE_SWEEP_SIZES,
    TILE_SWEEP_NAIVE_REFERENCE_MAX, OBLIVIOUS_PARAMS, OBLIVIOUS_SIZES.
  - The new checks are not in the default list, so "run all" works as before.

Seen in the data:
  1. The curve over the tile size is U shaped at n >= 1024, for both layouts. Very small tiles are
     much slower than the plain loop (T=4 at n=2048: 25 s against 4.7 s for row_wise, 5.3 times
     slower, also 19 s on the tile wise layout); the minimum is at T=128 in all four large cases;

     faster than row_wise: row major 2.2 times (n=1024) and 1.9 times (n=2048), tile wise 2.7 times
     (n=1024) and 2.6 times (n=2048).

     within noise. Tile wise at n=512 with T=64..128 is 7% to 17% faster than row_wise (29.1 and
     28.0 ms against 31.2 or 33.6 ms), at the edge of the noise.
  4. A tile that does not fit the cache (professor's question 4): the row major curve goes up
     steeply: from T=128 (2502 ms) to T=512 (5591 ms) at n=2048 it more than doubles, and T=512 is
     18% slower than row_wise (4735 ms). The tile wise curve is flat: T=128 1846 ms, T=256 2109 ms,
     T=512 2078 ms (+13%). The B tile alone is 128 KiB at T=128 (fits L2), 512 KiB at T=256 (= L2) and
     2 MiB at T=512 (fits L3 only). The steps follow the cache levels as predicted, but on the
     tile wise layout the penalty is much smaller. At n=1024 T=512 is faster than row_wise on both
     layouts (449 and 257 ms against 619 ms) because n=1024 still consists of 2 x 2 tiles.
  5. T = n (one tile) is the same as row_wise, as predicted: at n=512 T=512 gives 33.5 ms
     (row major) and 30.7 ms (tile wise) against 31.2 ms; at n=256 T=256 gives 4.0 ms.

Why the tile wise layout is faster was not measured on this day (no cache counters in this
session). Hypotheses: in the row major layout the rows of a tile are n*8 bytes apart (8 KiB
at n=1024, 16 KiB at n=2048), which maps them to few cache sets (conflict misses) and to many
different 4 KiB pages (TLB misses); in the tile wise layout a tile is one contiguous block, which
also suits the hardware prefetcher. All three effects would be largest for large tiles, which is
consistent with the data (-63% at T=512). Confirming this needs hardware counters for all layouts
(October has counters only for naive / row_wise / tiled; a 2026-11-15 attempt for all nine
versions was started and stopped, see 2026-11-15.txt).

  - row_wise does not get slower per operation than at n=2048: 3.66 GFLOPS against 3.63 GFLOPS
    (4735 ms at n=2048). The prediction of section 3, that row_wise loses more once the inner
    loop (a row of B and a row of C, 64 KiB at n=4096) no longer fits L1, was NOT seen. Possible
    reason (hypothesis, not measured): row_wise is already limited by streaming B from L3/RAM
    from n=1024 on, and that limit does not get worse when the rows leave L1.
  - Limits: only the row major layout, only three tile sizes, 3 repetitions, one session, no
    check of the noise at this size. Treat as indicative, not as a result of the same quality
    as 7.2 and 7.3.
  - Not measured: whether the tile wise layout and the oblivious versions keep their advantage at
    n=4096, and the tile sizes T=256 and T=512 there.


** 7.5 Answers to the planned questions and the predictions

  1. Best T: T=128 for n >= 1024 on both layouts (n=512 and 256: flat from T=32). The cache size
     predicted T=16..64 (tiles that fit L1). The measured optimum is the L2 sized tile (3 tiles
     of 128 x 128 doubles = 384 KiB, L2 = 512 KiB). T=64 is close behind. The prediction was
     partly wrong. (Reason not measured, see 7.2.)
  2. The curve goes up again for large T: T=256 is 11% to 14% above the best, and T=512 is
     much worse on row major (+59% at n=1024: 449 against 283 ms; +123% at n=2048) and mildly
     worse on tile wise (+11% at n=1024, +13% at n=2048).
  3. Tiling beats row_wise only for n >= 1024 on row major (2.2 and 1.9 times); at n=256 and
     n=512 there is no gain. October gave the same (gain only at n=1024; n=2048 is new).
  4. n = 4096: only partly measured (7.4). row_wise runs at the same speed per operation as at
     n=2048 (3.7 GFLOPS), and tiled with T=128 is 1.8 times faster than row_wise. The case
     "single row > cache" is therefore only covered by this indicative result (row major,
     T = 32..128); it is not fully measured. n=8192 (row clearly larger than L1) was not possible.
  5. Prediction of section 3: right for the U shape, for T=4/8 being slow, for T=512 being bad on
     row major, for T >= n equal to row_wise and for no gain at n <= 512. Wrong for the best T
     (L2 sized, not L1 sized) and for the worry about T=64 (no special penalty seen in run 2; the
     slow T=64 at n=2048 in the first run, 4271 ms, was noise).
  6. col_wise is as fast as row_wise (within 2%): column major mirrors row major for the plain
     loops. Column major tiled is similar to row major tiled, up to 20% slower at n=2048.
  7. Yes: the tile wise layout beats row major with the same tile size and the same loops, by
     13% to 18% (n=1024) and 25% to 32% (n=2048), and by 43% / 63% at T=512.
  8. Oblivious is as fast as the best cache aware version on every layout (within 7%, which is the
     noise level).
  9. They do depend on it somewhat: up to 21% between parameters on row major at n=2048, 13% on
     column major (not monotonic), up to 7% to 11% at n=1024 (see 7.3, point 5).
  10. Predictions of section 4: 1 wrong (oblivious is not slower), 2 right (oblivious is 2.0 to 2.7
      times faster than the plain loops at n >= 1024), 3 right for the plain loops and roughly right
      for tiled, 4 right (tile wise is the fastest layout at n >= 1024), 5 partly wrong (the
      parameter changes the time by up to 21%, not "hardly").


** 8. What is still missing / limits

  - Hardware counters for all nine versions / three layouts: not finished. October has counters
    only for naive, row_wise and tiled (row-major). A full-counter run was started on 2026-11-15
    (perf is available again) and stopped on purpose; see 2026-11-15.txt. Explanations of WHY the
    tile-wise layout wins (conflict misses, TLB, prefetching) remain hypotheses.
  - "Single row > cache" is only partly covered, on purpose because of wall time: work grows as
    n^3, so n = 4096 is about eight times more work than n = 2048 (one multiply ~20 to 40 s). The
    n = 4096 session was stopped after 4 runs (row major only, T = 32..128, see 7.4); a full
    sweep there was expected to take more than an hour. Tile-wise and oblivious at n = 4096 are
    not measured. n = 8192 (a row larger than L1) does not fit in the ~3 GB of WSL memory
    (needs about 2 to 3.5 GB). Large tile sizes (T up to 512) were measured at n <= 2048; they
    are not what made the runs too long.
  - One machine, one compiler, double, one thread. Noise is 3% to 7% (n >= 512).
  - Z order (the fully oblivious layout) is not implemented; oblivious_tile_wise still has the
    tile size in the layout.
  - The column major tiled versions differ up to 20% from row major tiled at n=2048, not explained.
  - Code not committed when measured (see section 6).
  - Charts for this day's data are in docs/01-matrix-multiplication/figures/2026-11-14-ryzen5500u-wsl2-run2/.
